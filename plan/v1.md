# Job Finder & Resume Matching Server — System Design & Build Spec

> **Purpose of this document:** This is a complete engineering specification meant to be handed to an AI coding assistant (or a human dev) as a single prompt to scaffold the entire backend server. It covers architecture, folder structure, API contracts, DB schema, scraping strategy, and integrations. Copy this whole file as the instruction when you start building.

---

## 1. What we're building

A backend server that:
1. Accepts a user's resume/profile details (skills, experience, target role, location preference).
2. Pulls job listings from a mix of **free/legal job APIs** and **Playwright-based scrapers** for individual company career pages.
3. Ranks fetched jobs against the user's resume using embedding-based similarity (no LLM fine-tuning needed for v1).
4. Returns a ranked list of matching jobs through a REST API, ready for a frontend to consume.

**Not in scope for v1:** auto-applying to jobs, scraping LinkedIn/Indeed/Glassdoor directly (ToS-hostile, bot-detected — use their absence as a deliberate design decision, not an oversight).

   └─────────┬───────────┘                              ▼
             │                               ┌────────────────────┐

   ┌─────────────────────────────────────────────────────────┐
   │                     PostgreSQL + pgvector                  │
   │   users | resumes | jobs | job_embeddings | matches        │

                  │  local, no API cost)     │
                  └───────────────────────┘

**Key design decisions:**
- FastAPI (async) pairs naturally with Playwright's async Python API.
- Scraping jobs run as **background Celery tasks**, never inline in a request — scraping is slow and flaky, so it must not block the API.
- Job matching uses local embeddings (`sentence-transformers`), not a paid LLM — keeps cost at $0 for the core loop.
- Postgres + `pgvector` extension stores embeddings alongside relational data — avoids running a separate vector DB for v1.

## 3. Tech Stack (all open source / free tier)

| Layer | Choice | Why |
|---|---|---|
| API framework | FastAPI | async-native, pairs with Playwright async API |
| Scraper | Playwright (Python, async) | handles JS-rendered career pages |
| Task queue | Celery + Redis | mature, well-documented, handles retries/backoff |
| DB | PostgreSQL 16 + `pgvector` | relational + vector search in one DB |
| ORM | SQLAlchemy 2.0 (async) + Alembic for migrations | standard, async-capable |
| Embeddings | `sentence-transformers` (`all-MiniLM-L6-v2`) | local, free, good enough for resume-job similarity |
| Resume parsing | `pyresparser` or custom spaCy pipeline | extracts skills/experience from raw text/PDF |
| Auth | JWT via `python-jose` + `passlib` | stateless, standard |
| Containerization | Docker + docker-compose | reproducible local + deploy setup |
| External job data | Adzuna API, Remotive API, Arbeitnow API, RemoteOK API | free, legal, structured JSON — no scraping needed for these |

## 5. Database Schema (core tables)

**users**
`id, email, hashed_password, full_name, created_at`

**resumes**
`id, user_id (FK), raw_text, parsed_json (skills, experience, education), target_role, target_location, remote_preference, created_at, updated_at`

**jobs**
`id, source (enum: adzuna|remotive|arbeitnow|scraped), source_url (unique), title, company, location, remote_type, description, salary_min, salary_max, posted_at, scraped_at`

**job_embeddings**
`id, job_id (FK), embedding (vector(384)), model_version`

**matches**
`id, resume_id (FK), job_id (FK), score (float), created_at`

**scrape_tasks**
`id, target_url, site_type, status (pending|running|success|failed), celery_task_id, result_count, error_message, created_at, finished_at`

## 7. Scraping Strategy (the part you asked to focus on)

**Tiered approach — don't scrape what you don't have to:**

1. **Tier 1 (no scraping):** Adzuna, Remotive, Arbeitnow, RemoteOK — official JSON APIs, free tier, legal, structured. This should cover the bulk of listings.
2. **Tier 2 (light scraping, low risk):** Company job boards hosted on `boards.greenhouse.io/*` and `jobs.lever.co/*` — these are semi-structured HTML, not adversarial toward bots, and many companies use them. Build one Playwright module per platform.
3. **Tier 3 (generic fallback):** Arbitrary company `/careers` pages — use a heuristic scraper (looks for common patterns: job title in `<h2>`/`<h3>`, links containing `/job/`, `/careers/`, `/position/`). Lower reliability, expect to maintain this over time.
4. **Explicitly excluded:** LinkedIn, Indeed, Glassdoor — ToS-prohibited scraping + heavy bot detection. Not worth the legal/technical risk for a resume tool.

**Playwright implementation notes for the AI builder:**
- Use `playwright.async_api`, run headless Chromium.
- One shared `BrowserManager` class that maintains a browser instance pool — don't spin up a new browser per request, it's expensive.
- Each site module (`sites/greenhouse.py` etc.) implements a common interface: `async def scrape(url: str) -> list[JobListing]`.
- Add random delays between actions (`anti_detection.py`) and respect `robots.txt` — check it programmatically before scraping any new domain.
- Run scrapers **only inside Celery workers**, never in the request/response cycle.
- Store `scrape_tasks` rows so retries and failures are visible via the `/scrape/status/{task_id}` endpoint.

## 8. Matching Pipeline

1. On resume save → Celery task embeds `parsed_json` text via `sentence-transformers` → stores in `resumes.embedding` (or a related table).
2. On job save (from aggregator or scraper) → Celery task embeds `title + description` → stores in `job_embeddings`.
3. `POST /match/{resume_id}` computes cosine similarity between resume embedding and all job embeddings (via `pgvector`'s `<=>` operator for efficient nearest-neighbor search), returns top N sorted by score.
4. v1 has **no fine-tuning** — pretrained embeddings are sufficient. Revisit fine-tuning only once there's real usage/feedback data to train on.

## 9. Build Instructions For The AI Coding Assistant

When implementing this spec:
1. Scaffold the folder structure exactly as in Section 4.
2. Implement DB models + Alembic migration for Section 5's schema first.
3. Build `/health` and `/health/ready` first to confirm the skeleton runs.
4. Implement `integrations/` (Tier 1 APIs) before `scraper/` — get non-scraping data flowing end-to-end first.
5. Implement `scraper/browser_manager.py` and one working site module (`greenhouse.py`) before generalizing to the generic fallback.
6. Wire Celery + Redis, confirm a scrape task can be queued and polled via `/scrape/status/{task_id}`.
7. Implement `embedding_service.py` and `matching_service.py` last, once jobs and resumes are flowing into the DB.
8. Write integration tests for scrapers using Playwright's route interception/mocking — never hit live external sites in automated tests.
